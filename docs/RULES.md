# 実習のルール

## 実習フロー

1. **仕様の確認**: `docs`フォルダにある仕様書等を読み、要件を理解する。
2. **プログラム作成**: `programs`フォルダにプログラムIDのフォルダを作成し、COBOLプログラムを作成する。
3. **テストデータの準備**: プログラムと同じフォルダにテストデータを用意する。
4. **ビルドとテスト実行**: プログラムをコンパイルし、テストを実行する。
5. **デバッグ**: 問題があれば修正し、動作確認を行う。
6. **チェックリストの作成**: 実施したテスト項目を`CHECKLIST.md`にまとめ、結果を記録する。
7. **チェックリストのレビュー依頼**: 作成した`CHECKLIST.md`をレビュー担当者に提出し、テスト項目が網羅的かつ適切であるか確認を依頼する。
8. **最終レビュー依頼**: チェックリストが承認された後、プログラム本体と合わせて再度提出し、最終的なレビューを受ける。

---

## AI利用のルール

* AIエージェントはあなたのアドバイザー役として動作します。
* プログラムの説明、作成する上のヒント、テストデータの作成、チェックリストの作成の補助を行います。
* 本AIエージェントは本研修にのみ利用できます。

## 名前

### システムID

* 文字数：1
* 研修の`K` 固定

### 機能ID

* 文字数：1
* `J`: 受注処理
* `U`: 売上処理
* `C`: 共通処理

### 処理形態

* 文字数: 1
* `B`: バッチ処理

### モジュール形態

* 文字数: 1
* `M`: メインプログラム
* `S`: サブプログラム

### プログラムID

`<システムID><機能ID><処理形態><モジュール形態><連番>`

* 文字数: 7
* 連番: 3文字。頭0付きの10進数。原則10刻みの連番。
* 例: `KJBM010`

### コピー句ID

`<システムID><機能ID>C<ファイル区分><識別子>`

* 文字数: 7以上
* ファイル区分: 1文字。
  * `F`: 一般ファイル
  * `M`: マスタファイル
* 識別子: 3文字以上。英数字。
* 例: `KCCFSHO`、`KJCF010`

### ファイル名

* COBOLプログラム: `<プログラムID>.cob`
* 埋込みSQLを含むプログラム: `<プログラムID>.cbl`
* マスタデータ: `<コピー句ID>.dat`
* 入力データ: `<プログラムID>I<連番>.dat` ※<連番>はなくても良い
* 出力データ: `<プログラムID>O<連番>.dat` ※<連番>はなくても良い
* コピーブックファイル: `<コピー句ID>.cbl`

### 項目名

`<プログラムID|コピー句ID>-<名前>`

* 文字数: 7以上
* プログラムID|コピー句ID の一部。3文字以上。
* 名前: 英数字ハイフン。項目の意味が伝わる名前とする。
* 例:
  * `JF020-DATA-KBN`
  * `CFSHO-SHOHIN-NO`

## ファイルの配置

```
/
├─── copylib/...                # COBOLコピーブックファイルを配置するフォルダ
├─── docs/...                   # 実習用ドキュメント用フォルダ
├─── extra/...                  # その他のユーティリティや補助スクリプトを配置するフォルダ
├─── programs/...               # COBOLプログラムのソースコードと関連ファイルを配置するフォルダ
└─── sample/...                 # COBOLサンプルプログラムを配置するフォルダ
```

### programs内フォルダ内配置

```
programs
├─── <PROGRAM-ID>               # プログラム格納用フォルダ
       ├─── build.sh            # 実行プログラム作成用スクリプト
       ├─── run.sh              # 実行プログラム実行用スクリプト
       ├─── CHECKLIST.md        # プログラムチェックリスト
       ├─── <PROGRAM-ID>        # 実行プログラムファイル    
       ├─── <PROGRAM-ID>.COB    # ソースコード
       └─── <PROGRAM-ID>.CBL    # Embedded SQLを含むソースコード(オプション)
```

例) KJBM010の時

```
programs
├─── KJBM010
       ├─── build.sh
       ├─── run.sh
       ├─── CHECKLIST.md
       ├─── KJBM010
       └─── KJBM010.COB
```

## コーディング規則

### 1. ソースコード形式

* **固定形式**: 標準の固定形式（7カラム目に標識、8-11カラムにA領域、12-72カラムにB領域）を厳守する。
* **大文字**: すべてのソースコード（予約語、ユーザー定義名を含む）は、必ず大文字で記述する。
* **コメント**:コメント行は7カラム目にアスタリスク(`*`)を記述する。
* **見出し**: `IDENTIFICATION DIVISION`の`PROGRAM-ID`の直後に、以下の形式でプログラム情報を記述する。

```cobol
       IDENTIFICATION  DIVISION.
       PROGRAM-ID.     KJBM010.
      ******************************************************************
      * システム名　　：研修
      * サブシステム名：<サブシステム名>
      * プログラム名　：<プログラム名>
      * 作成日／作成者：2026/01/09　[自分の名前]
      * 変更日／変更者：
      * 　　　変更内容：
      ******************************************************************
      
```

### 2. 命名規則

データ名は、原則として`<プログラムID|コピー句ID>-<名前>`の形式とし、さらに以下の用途別識別子を付与する。

| 種類           | 命名規則（例） | 備考                                 |
| -------------- | -------------- | ------------------------------------ |
| **ファイル名** | `XXX-FILE`     | `SELECT`句で使用するアクセス名       |
| **レコード名** | `XXX-REC`      | 複数ある場合は `XXX-REC1` 等         |
| **フラグ**     | `XXX-FLG`      | `ON-FLG`, `ITF-END-FLG` 等           |
| **スイッチ**   | `XXX-SW`       | `FIRST-SW`, `BREAK-SW` 等            |
| **カウント**   | `XXX-CNT`      | `ITF-CNT`, `ERR-CNT` 等              |
| **テーブル**   | `XXX-TBL`      | `OCCURS`句を伴うデータ               |
| **見出し領域** | `Hn-XXX`       | 印刷用（nは連番）                    |
| **明細領域**   | `Dn-XXX`       | 印刷用（nは連番）                    |
| **作業領域**   | `WK-XXX`       | `WORKING-STORAGE`内の上記以外の項目  |

### 3. コーディングスタイル

#### 手続き部（PROCEDURE DIVISION）の構造

##### **基本フロー**

原則として以下の構造で記述し、各処理はセクション(SECTION)化する。

* `PERFORM INIT-RTN.` （初期処理）
* `PERFORM MAIN-RTN UNTIL ITF-END-FLG = 'Y'.` （主処理：終了フラグまでループ）
* `PERFORM TERM-RTN.` （終了処理）

##### **セクション定義**

* セクション名は末尾を `-RTN` とする。
* セクションの終わりには、必ず `EXT.`（段落名）と `EXIT.`（命令）を記述する。
* 各セクションの前には、処理内容を記したコメントブロックを入れる。

``` cobol
      ******************************************************************
      * 主処理
      ******************************************************************
      MAIN-RTN  SECTION.
          READ ITF-FILE AT END
            SET ITF-END-FLG TO 'Y'
          END-READ.
          ...
      EXT.
          EXIT.
```

#### 制御構文と字下げ

* **範囲明示命令**: `IF`には`END-IF`、`EVALUATE`には`END-EVALUATE`を使用し、ピリオドは原則として各文の終わりにのみ使用する。
* **インデント**: 命令文が入れ子になる場合は、**2桁ずつ**字下げを行う。
* **GOTOの禁止**: 構造化プログラミングを維持するため、特別な理由がない限り `GO TO` は使用しない。

#### コンソールメッセージ（DISPLAY）

プログラムの稼働状況を把握するため、以下のメッセージを表示する。

##### **開始時**

```
*** <PROGRAM-ID> START ***
```

##### **終了時**

入出力を行ったレコード数を表示する。

```
*** <PROGRAM-ID> <アクセス名>: 999999999
*** <PROGRAM-ID> END ***
```

### 4. 通常処理(NORM-END)

エラーなくプログラムを終了する場合は、次のように対応する。

- 入出力したレコード数をアクセス名ごとに表示する。
- ファイルを閉じる。
- `RETURN-CODE` に 0 を設定する。
- `STOP RUN`を実行し、プログラムを終了する。

### 5. エラー処理（ABEND）

ファイルのOPEN失敗やSQLエラーなど、続行不能なエラーが発生した場合は以下のように対応する。

* 共通エラー処理セクション（`999-ERROR-RTN`）を `PERFORM` する。
* **ABENDメッセージ**: `*** <PROGRAM-ID> ABEND <原因がわかるメッセージ>` を表示する。
* `RETURN-CODE` にゼロ以外の値を設定し、`STOP RUN` を実行する。

### 6. プログラム実行時のコンソールメッセージ出力例

正常時は、入出力したレコード数を表示すること、

```
*** KJBM010 START ***
ITF-CNT: 000000100
OTF-CNT: 000000100
*** KJBM010 END ***
```

異常終了時は、理由を表示すること。

```
*** KJBM010 START ***
*** KJBM010 ABEND ITFが読み込めませんでした。
```

## プログラムチェックリスト

各 program_id フォルダに `CHECKLIST.md` を作成し、この内容をもとにプログラムをチェックします。

### チェックリストの書式

```markdown
# <program_id> 単体テストチェックリスト

## 確認内容の概要

確認内容

- [x] チェック項目1
- [ ] チェック項目2
```

### Markdownチェックリストの具体例

研修教材にある「受注データ形式チェック (KJBM020)」の仕様に基づき、受講生には以下のようなテキストファイルを作成させます。

**ファイル名: `TEST_KJBM020.md` の記述例**

```markdown
# KJBM020 単体テストチェックリスト

## 形式チェック（正常系・異常系）
仕様書「チェック詳細」 に基づく確認

- [x] (1) データ区分が '1' の場合、エラー区分(1)がスペースであること
- [ ] (1) データ区分が '5' (不正値) の場合、エラー区分(1)に '1' がセットされること
- [x] (2) 受注番号が数字かつゼロでない場合、エラー区分(2)がスペースであること
- [ ] (4) 商品番号が数字かつ1〜999の範囲内の場合、エラー区分(5)がスペースであること
```

### この方式を採用する意図

この形式には、従来のExcel管理と比較して以下のメリットがあり、本事業の「モダンな開発体験」および「AI活用の効率化」に直結します。

1. **AIが読み書きしやすい（自動評価の実現）:**
    * Excelファイルは構造が複雑で、AI（ChatGPTやGitHub Copilotなど）に内容を理解させたり、結果を判定させたりするのが困難です。
    * Markdownであれば純粋なテキストデータであるため、AIに「このチェックリストの項目を網羅するテストデータを作成せよ」や「ログファイルと照合してチェックボックスを埋めよ」といった指示が容易に出せます。
2. **Git/GitHubとの親和性:**
    * 研修のポイントとして「ソースコードのレビューはGitHubを経由した方法で行う」とあります。
    * Markdownチェックリストであれば、ソースコードと同じリポジトリでバージョン管理でき、講師はブラウザ（GitHub）上でチェックリストとコード、実行ログを並べてレビューできます。
3. **進捗の可視化:**
    * GitHubのIssueやPull Requestの本文にこのテキストを貼り付けると、`[ ]` がインタラクティブなチェックボックスとして表示され、進捗状況（例：2/4 完了）がプログレスバーとして可視化されます。

### 運用イメージ

受講生には以下のフローで作業させます。

1. VS Code上で `CHECKLIST.md` を作成し、仕様書からテスト項目を書き出す。
2. プログラムを実行し、ターミナルに出力されたログや出力ファイルを確認する。
3. 確認できた項目の `[ ]` に `x` を入れて `[x]` にする（チェック済みとする）。
4. このファイルをソースコードと共にGitHubへコミット・プッシュする。

このように、**「Excelという事務作業」を「エンジニアリング（Markdown記述）」に置き換える**ことで、学習のモチベーション維持と効率化を狙う施策となります。

## レビューのルール

### 1. レビューの目的

* コードの動作を理解しているか確認する。
* コードの品質（可読性、保守性、効率性）の向上を図る。
* プログラムが要求仕様を正確に満たしているかを確認する。
* 潜在的なバグや設計上の問題を早期に発見し、修正する。
* 講師(上長)の承認を得るという行為を訓練する。

### 2. レビュー担当者（レビュアー）の役割

* **建設的なフィードバック**: 改善点を明確かつ具体的に伝え、解決策の提案も検討する。
* **仕様との照合**: プログラムが仕様書通りに実装されているかを確認する。
* **テスト内容の確認**: 提出された`CHECKLIST.md`を確認し、テスト項目が適切かつ網羅的か、またテスト結果が正しく記録されているかを評価する。
* **効率性**: 非効率な処理がないかを確認する。

### 3. レビューを受ける側（レビュイー）の役割

* **明確な説明**: レビュー依頼時に、変更の目的、実装の意図、懸念点などを明確に説明する。
* **必要情報の提供**: 関連する仕様書、テストデータ、テスト結果（`CHECKLIST.md`を含む）などを準備し、レビュアーがレビューしやすいように提供する。
* **フィードバックの検討**: レビュアーからの指摘や提案を真摯に受け止め、改善策を検討し、適切に対応する。
* **質問**: 不明な点や疑問点があれば、積極的に質問し、理解を深める。

### 4. レビューのプロセスとツール

* **Pushベース**: Git/GitHubにプッシュし、それを連絡する事でレビューを行うことを基本とする。
* **コメントと議論**: GitHubのコメント機能や、必要に応じて対面またはオンライン会議を活用し、議論を深める。
* **完了の判断**: レビュアーとレビュイー間で全ての指摘が解決し、コードが承認された時点でレビュー完了とする。

### 5. コミュニケーションガイドライン

* **コードへの言及**: フィードバックは、コードの具体的な内容に対して行い、個人攻撃にならないよう注意する。
* **尊重の姿勢**: 異なる意見がある場合でも、互いの意見を尊重し、建設的な議論を心がける。
